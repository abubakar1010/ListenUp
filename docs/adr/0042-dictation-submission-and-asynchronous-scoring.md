# ADR 0042: Dictation submission and asynchronous scoring

- Status: Accepted
- Date: 2026-10-18
- Source: issue #54; [SRS FR-DI-5, FR-TX-5, FR-DI-3, NFR-USE-2, AT-3](https://claude.ai/code/artifact/fd47a9cb-6515-4fde-a232-3ab8cc14f0dd); [Architecture 5.3, 9.2](https://claude.ai/code/artifact/6a30920f-b6a0-4131-a486-f2044c71bb13); [System Design 3.1, 4.1](https://claude.ai/code/artifact/98274889-96ba-4424-afad-c2cd056206e2); ADR 0008, 0019, 0021, 0025, 0038

## Context

Submitting Dictation must complete the step and show missing, wrong, spelling-slip and extra words with an accuracy. The reference words come from the passage transcript, which may still be running (System Design 3.1: the text is saved and scored when the transcript arrives). The API role has no grant on the transcript cache, no worker-role database is wired into API requests (ADR 0038 leaves that to the Transcript route), and `read_passage` requires the Transcript step, which a learner in Dictation has not reached.

## Decision

- **Submit never scores.** `POST /dictation/attempts/{id}/submit` (body: `text`, the session `version`, `replay_count`; `Idempotency-Key`) answers 202 with the attempt status and `scoring_status`. In one transaction it stores `submitted_text` with `scoring_status = 'waiting_transcript'`, finishes the attempt, completes the Dictation step, records `dictation_replays` and queues the scoring job. The step never waits for the transcript, and the answer never holds the diff. Refusals: 404 `attempt_not_found`; 409 `step_locked` (also for a resubmit, because the step is complete), `session_closed`, `session_changed`, `attempt_closed`; 422 `empty_submission`, `submission_too_long`. The text in the body is authoritative; the draft is left as it was.
- **One scoring path.** Job `dictation.score_attempt(attempt_id, user_id)` on the `ai` lane (the learner is waiting; scoring is a pure-Python diff and a few queries, so it takes none of the two media slots that transcription and Shadow analysis need, and the lane's eight async slots on the default pool keep latency low). It reads the passage words through `transcript.service.reference_for_scoring`, which checks ownership and `require_reached(DICTATION)` and shares `read_passage`'s cache read, then runs the pure `score_dictation` and stores the diff and accuracy in one conditional update (`WHERE scoring_status = 'waiting_transcript'`) that also publishes `dictation.scored` with the attempt id. A second run finds nothing to update and announces nothing. A transcript that is not ready leaves the row waiting and the job returns (no retry). A transcript that failed makes the row `scoring_unavailable` and publishes `dictation.scored` once, so the screen can say it cannot score (grading never blocks the learner); a later successful transcription queues it again and it is scored. A session or clip that no longer exists ends the job quietly.
- **Waiting submissions continue when the transcript arrives.** After `transcript.ready` is published, the transcript job calls `transcript.service.announce_ready`, which runs hooks that modes registered with `on_passage_ready` (Dictation registers `on_transcript_ready` from `dictation/jobs.py`). A direct import from `transcript.jobs` to `dictation.service` would give `practice` an indirect path to a mode module (import-linter), so the dependency is inverted. The transcript job commits `transcript.ready` first and runs the hooks in a second transaction scoped to the learner, so a hook that fails retries the job without losing the event. `on_passage_failed` does the same after `transcript.failed`, which moves a waiting submission to `scoring_unavailable`. The scoring job has no `unique_key`: a key also matches a running job and would swallow the hook's queueing while a job that found no transcript is still running; a repeat stops after reading the submission once it is scored. Every worker pool imports `dictation.jobs` through `JOB_MODULES`, and a test pins that the hooks are registered. The cache commits before the hook runs, and a submit queues its own job after its commit, so one of the two always sees the other.
- **Reading.** `GET /dictation/attempts/{id}` and `GET /sessions/{id}/dictation/attempt` (newest attempt, also after the step is complete) return the state and, when scored, `result`: `accuracy`, `counts`, and one ordered `items` list (`index`, `status`, `word`, `typed`; extra words sit where they were typed). The reference text is in `result.items[].word` only, after scoring, and in no other response (FR-DI-3, FR-TX-5); mark candidates are not exposed (#55).
- **Corrections.** Scoring uses the passage transcript. The seam for the learner's own corrections is `dictation.service.reference_words`; #56 applies them there and re-scores through the same function.
- **Web.** The Dictation screen submits; the session page shows `DictationResultPanel` under the next step whenever Dictation is done. While waiting it says "Scoring when the transcript is ready"; `dictation.scored` invalidates the Dictation result queries and the diff replaces the message without a reload. Each status has a text label and a line style as well as a colour (spelling slip dotted, missing dashed, wrong wavy, extra struck through; NFR-USE-2, WCAG 1.4.1).

## Consequences

- Every submit shows the waiting message for a moment, even with the transcript cached, because the API cannot read the cache. Wiring a worker-role connection into the API for an inline fast path remains possible and would not change these contracts.
- A failed transcription shows "We could not score this Dictation" with the plan continuing. Retrying transcription is not part of this story; when it succeeds later, the score appears.
- `submit` closes the attempt with its conditional update before it stores the text, so of two concurrent submits only one passes and the other is refused without a trace.
- `dictation.scored` is a signal with an id only; the browser refetches the result through the normal access checks.
