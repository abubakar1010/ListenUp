# ADR 0022: Upload conversion, duplicate uploads and media delivery

- Status: Accepted
- Date: 2026-10-03

## Context

Issue #36 turns a confirmed upload into the playback file (Architecture 5.1, System Design 6.1) and lets the learner play it (Architecture 9.2, `GET /media/{media_object_id}`). ADR 0020 moved the SHA-256 fingerprint into this job and left two questions to it: what happens when the learner uploads a file they already have, and whether the daily limit of new audio (FR-CI-3, D16) is enforced here. The design documents also leave open what exactly counts as an unusable file, how long a clip may be, where the files live and what the peaks file looks like.

## Decision

- **One job, safe to repeat.** `content.convert_upload` (intake lane, media pool) reads the media object, streams the original into a scratch directory (`LISTENUP_MEDIA_SCRATCH_DIR`, else the system's) while hashing it, probes, converts, stores the outputs, then sets `playable` and publishes `content.ready` in one transaction, and only then deletes the original. A run on a media object that is already `playable` or `failed` only deletes the original again; a run for an item that was deleted does nothing. ffprobe and ffmpeg run with `asyncio.create_subprocess_exec` and are killed if the job is cancelled.
- **What is refused, for good.** Only ffprobe's view of the bytes counts. The container must be one of the accepted upload types (ffprobe's `mp3`, `wav`, `mov`/`mp4`/`m4a`, `matroska`/`webm`); anything else, including a file ffprobe cannot read, is `unsupported_media`. A file without a sound track is `no_audio_track`; one shorter than 30 s, the shortest passage (C2), is `clip_too_short`. There is no upper length limit: the learner picks a passage of at most 15 minutes from a longer clip. A missing original is `upload_missing` and an ffmpeg failure on a file that probed well is `conversion_failed`. Each sets the media object `failed` with that `error_code`, deletes the original, publishes `content.ready` and raises `PermanentError`. A transient error (storage down) is retried; on the lane's last attempt the item becomes `failed` with `processing_failed`, so it never stays "processing" for ever. The learner-facing sentences for the codes live in `content/domain/media.py`; the API returns both the code and the sentence.
- **Outputs.** The playback file is AAC-LC, mono, 64 kbit/s, MP4 with faststart, plus H.264 360p (never upscaled, `veryfast`, CRF 28) only when the item has `keep_video` and the file has a real picture track (an MP3's cover art is not one). It is one file, `playback_key`; `video_key` stays unused. Waveform peaks come from the same ffmpeg run (a second output of 8 kHz samples to a pipe), ten values a second on a 0 to 100 scale, stored as compact JSON (`{"version":1,"per_second":10,"scale":100,"peaks":[...]}`, under 2 KB a minute). Both live under `users/<user id>/media/<media id>/`, so deleting the account's prefix removes them. `duration_ms` is the sound track's length.
- **Duplicate uploads are merged into the older item.** Once hashed, the job sets the fingerprint `upload:<user id>:<sha256>`. If the learner already has an item on a media object with that fingerprint, the new item and its media object are deleted (its upload row goes with it, so it stops counting towards the storage cap; the reference-count trigger counts down), the original is deleted, nothing is converted, and `content.ready` is published for the removed item so a page showing it refetches and learns it is gone. The older item is kept because it may already have practice history and its playback file. The alternative of pointing the new item at the existing media object is impossible while the older item exists, since a library holds a media object once (`UNIQUE (user_id, media_object_id)`), and keeping both as separate items would break that rule in spirit. If the media object with that fingerprint has no item any more (the learner deleted it and the orphan sweep has not run), it is deleted with its files and the new upload takes the fingerprint and is converted normally. Uploads are never matched across learners, since the fingerprint includes the user id.
- **The daily limit of new audio is not enforced here; it is left to #41.** The SRS (FR-CI-3) asks to reject intake beyond 120 minutes of new audio a day with a clear message, while the System Design (4.2, admission control) says excess intakes wait in the learner's own queue instead. Counting a whole uploaded clip would also make any clip over 120 minutes impossible to add, although C2 lets a learner practise a passage of a long clip. Settling this needs the rejection-message story #41. Everything it needs is stored: `duration_ms`, `uploaded_by` and `created_at` on each upload's media object.
- **Delivery.** `GET /media/{media_object_id}` and `GET /media/{media_object_id}/peaks` look the media object up through the caller's own content item (and row-level security), so another learner, or anyone for a media object that does not exist, gets the same 404 `media_not_found`. An owner whose media is not `playable` yet gets 409 `media_not_ready`. Otherwise the answer is a 307 redirect, marked `Cache-Control: private, no-store`, to a signed GET URL from `S3Storage.signed_download`, which reuses a URL until 80% of its lifetime. The browser's player then sends its range requests straight to storage (System Design 6.4). `GET /contents/{id}` returns the item with its status, `error_code`, `error_detail`, and `media_url` and `peaks_url` (the two API paths above) once it is playable. `POST /contents` accepts `keep_video` (default false).

## Consequences

- A learner who uploads the same file twice sees the second item disappear from the library a few seconds after confirming it; the content page then says the clip is not in the library. A dedicated message ("you already have this clip") would need the removed item's id to be remembered, for example in a small table; this can come with #41's rejection messages.
- The storage cap still counts the uploaded size of confirmed uploads, not `playback_bytes`, which the job now records. Switching the count is left to the storage-cap work.
- A failed item keeps its upload row (and so counts towards the cap) until the learner deletes it; deleting an item (FR-CI-7) is a later story.
- A job that hits the intake lane's 10-minute timeout is cancelled; its last attempt then leaves the item `pending`, because the failure can only be recorded after cancellation. Very long video uploads with `keep_video` are the only realistic case; per-job CPU limits and a duration cap belong to the Hardening epic.
- Worker scratch files are removed at the end of every job; the hourly sweep of leftovers (System Design 6.3) is still to be built.
