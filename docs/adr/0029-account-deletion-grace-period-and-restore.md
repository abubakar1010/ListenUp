# ADR 0029: Account deletion with a 7-day grace period, a purge job and restore on sign-in

- Status: Accepted
- Date: 2026-10-04
- Source: issues #91 and #120; [SRS FR-ACC-1, FR-ACC-4, DR-1, NFR-SEC-5](https://claude.ai/code/artifact/fd47a9cb-6515-4fde-a232-3ab8cc14f0dd); [Software Architecture 9.2 (Account), 12.2](https://claude.ai/code/artifact/6a30920f-b6a0-4131-a486-f2044c71bb13); [Database Design 7 (`ops.deletion_requests`) and 10.1](https://claude.ai/code/artifact/ba05f7b3-f881-41e5-86d6-dcb94a509644); D9, D17; ADRs 0013, 0015, 0016, 0017 and 0030

## Context

D9 (confirmed 2026-10-03) replaced immediate account deletion with a 7-day grace period: the account is disabled at once and can be restored by signing in within 7 days; after that everything is deleted. The SRS (DR-1) and the Architecture (12.2) already say so, and Database Design 10.1 describes it with `users.status = 'pending_deletion'` and `deletion_scheduled_at`, writing `ops.deletion_requests` only when the period ends. Issue #91 instead asks for the request row to be written at once with its due time, and #120 asks that sign-in shows the date and asks before restoring, rather than restoring silently as the code did. The design does not say how a restore is confirmed, how a scheduled job is declared on the job lanes, or how open live-event streams learn that the account is gone.

## Decision

- **States.** `DELETE /me` sets `identity.users.status = 'pending_deletion'` and `deletion_scheduled_at = now() + LISTENUP_ACCOUNT_DELETION_GRACE_DAYS` (default 7), as Database Design 10.1 says, rather than `'deleting'` as #91 words it. `'deleting'` keeps its design meaning: the purge has started, and the account can no longer sign in or be restored. Keeping the two states apart is what lets the existing constraint (`pending_deletion` exactly when there is a date) and index (`users_deletion_due_idx`) stay as they are.
- **The request row is written at once** (as #91 asks): `ops.deletion_requests` (migration 0013) gains `due_at` (equal to `deletion_scheduled_at`), `cancelled_at` with status `'cancelled'`, `failed_at` with status `'failed'` (the purge gave up, see below), and `media_object_ids` (the learner's upload media objects, for the report). A restore cancels the request instead of deleting it, so every deletion and every restore leaves an audit row. At most one open account request per learner (partial unique index). The table has no foreign key to the learner, because it outlives the account; row-level security limits the API to the signed-in learner's own requests, and the API may not delete them.
- **Deleting** needs the current password and `confirm: true`. Wrong passwords answer 403 `wrong_password` and count towards the sign-in lockout (D17), so a stolen session cannot be used to guess the password. In the same transaction every login session ends, unused password-reset links are retired, the confirmation email is queued (`identity.send_deletion_notice`, sent from the background lane through notifications, ADR 0017; it states the date in UTC and links to sign-in) and `account.disabled` is published. The answer is 202 with `deletion_scheduled_at`, and the session cookie is cleared.
- **Disabled means disabled.** `identity.resolve_auth_session` now returns a learner only while the account is `active`, so every endpoint behind `CurrentLearner` and the events stream refuse with 401 `not_signed_in` even if a login session row survived. The event hub forwards `account.disabled` and then ends that learner's open streams; the browser's reconnect gets 401. The web app maps `account.disabled` to the `['me']` query, so other tabs go to sign in.
- **Restore (#120).** Signing in with the right password to an account inside its grace period answers 409 `account_pending_deletion` with `deletion_scheduled_at`, and starts no session. Signing in again with `restore: true` reactivates the account (only while `deletion_scheduled_at > now()`, under the row lock the purge also takes), cancels the request and starts a session; all data is untouched. Declining is simply not sending the second call: nothing was signed in, and the deletion stays scheduled. After the grace period, sign-in answers 401 `invalid_credentials` with the normal message, with or without `restore`, and password-reset requests send nothing, exactly as for an unknown email. A reset link from before the deletion no longer works, and a reset asked for before the deletion whose email job had not run yet sends nothing (the job carries `requested_at` and compares it with the request's); a reset asked for during the grace period works but starts no session, so the data stays out of reach until the learner signs in and confirms the restore. Every sign-in method ends in `Accounts.complete_sign_in`, which owns this rule; Google sign-in (#32, not built) must call it too, and its accounts (no password) get 409 `reauthentication_unavailable` from `DELETE /me` until Google re-authentication exists.
- **Scheduled jobs.** `@job(..., schedule="<cron>")` declares a job that also runs on a schedule (UTC). `install_schedules(lanes)` turns schedules on, and only worker processes call it, for the lanes their pool serves, so the API and tests never queue scheduled work by themselves. Procrastinate records each tick, so several processes queue it once.
- **Purge.** `identity.purge_due_accounts` runs every 15 minutes on the background lane and queues one `identity.purge_account` job per due, open request (unique key and lock per request; a failed purge is queued again by a later sweep). The purge: sets the account `'deleting'` and ends any session; deletes the storage prefix `users/<id>/` and marks the request `storage_deleted`; deletes the `identity.users` row (cascades remove every learner row, and the reference-count trigger releases shared media, which stays for other learners) and completes the request with a report (`rows_removed` per table, `rows_total`, `objects_removed`, `media_objects`) in the same transaction; then sweeps the prefix once more for files a job still running for the learner wrote meanwhile. Every step checks the request's state, so re-running is safe, and an active account is never purged.
- **A purge that gives up stays visible.** `identity.purge_account` has a 30-minute timeout and 3 attempts, and passes `on_give_up` (`platform/jobs.py`): when the last attempt fails or times out, the request becomes `'failed'` with `failed_at`, and its report counts `failures` and names the `failed_step` (`'pending'` or `'storage_deleted'`). The request stays open (it still blocks a second request and is still due): the sweep queues it again once `failed_at` is an hour old, and the purge resumes from the storage step, which is safe to repeat. Meanwhile the account cannot sign in or be restored, because its grace period has ended. The operator sees the half-done purge as a `'failed'` row and an error in the worker log; a failed purge is never silently dropped, because a deletion must finish (DR-1).
- **Data export (ADR 0030).** A disabled account cannot start an export, because `POST /me/exports` needs a login session that resolves to an active account. An export asked for just before the deletion is not built: the build job checks `identity.service.account_is_active` and marks the export `'failed'` with `account_deleted`, storing nothing. The purge deletes the export archives with everything else under `users/<id>/`, and the `ops.data_exports` rows go with the account (they cascade from `identity.users`). The learner's own deletion requests (cancelled ones, after a restore) are part of their export, without the internal `storage_prefixes`.

## Consequences

- The design documents need these updates (not made here): Database Design 7 (the `ops.deletion_requests` DDL with `due_at`, `cancelled_at`, `failed_at`, `media_object_ids`, statuses `'cancelled'` and `'failed'`, the two indexes and the `own_requests` policy) and 10.1 (the request is written when the learner deletes, not when the period ends; the restore cancels it; `resolve_auth_session` checks `status = 'active'`); Software Architecture 9.2 and the API table (`DELETE /me` takes the password and `confirm`, answers 202 with the date instead of "deletes everything"; `POST /auth/login` takes `restore` and may answer 409 `account_pending_deletion`); the live-event lists in Software Architecture 9.1 and System Design 9.1 (`account.disabled`); System Design 4 (scheduled jobs on the background lane: the 15-minute purge sweep).
- Files of an upload still converting when the purge runs are caught by the final prefix sweep only if they land before it; a later straggler stays until a storage clean-up job exists. Shared YouTube media whose reference count drops to zero is left to the orphan clean-up that the System Design describes, which content deletion (#89) builds; until then such rows stay with `ref_count = 0`.
- A request's `report` holds counts and media object ids only, never content, so the audit row may be kept after the account is gone.
